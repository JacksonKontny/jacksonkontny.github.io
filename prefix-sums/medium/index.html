Prefix sums, from O(1) range queries to parallel scans

One row of running totals answers any range-sum question with a single subtraction. Building that row looks stubbornly sequential, yet SIMD units and GPUs build it in parallel. Here is how both halves work, traced by hand on eight numbers.

This is the static version of an interactive explainer. The interactive version lets you drag ranges, step through both parallel scans one add at a time, and answer the quick checks as you go.

The question: the sum of any slice, asked many times

Say a program holds an array a of n numbers and keeps asking the same kind of question: what is the sum of a[i..j]? Not once, but thousands of times, for thousands of different (i, j) pairs. Adding up the slice each time costs O(n) per question, so Q questions cost O(n·Q).

There is a better deal. Spend one pass building a second row: a running total that starts at 0 and adds each element in turn. Here it is for a five-element array.

Each number in the bottom row sits on a boundary between elements, because it is the total of everything before that boundary. So the sum of a[1..3] is the total before index 4 minus the total before index 1: 16 − 5 = 11, the same as adding 2, 8 and 1 one by one. A slice of three elements and a slice of three thousand cost the same: one subtraction.

That bottom row is a prefix-sum array. If you have ever called cumsum, you have built something very close to one; the small difference matters, as the first check below shows.

Why the subtraction always works

From here on, one slightly longer array runs through every figure: [3, 1, 7, 0, 4, 1, 6, 3].

Read prefix[k] as “the sum of everything before index k”. Then prefix[0] is the sum of nothing, which is 0, and prefix[8] is the sum of the whole array. That reading is why the array has n + 1 entries for n values: there are n + 1 places to stand, one before each element and one after the last.

Now take any range from i to j, inclusive and 0-indexed. “Everything before j + 1” contains the range plus everything before i. “Everything before i” contains just that front part. Subtract, and the front part cancels, because it is in both. What is left is exactly the range:

sum(i..j) = prefix[j+1] − prefix[i]

The algebra is a telescoping sum: prefix[j+1] − prefix[i] = (a₀ + a₁ + … + aⱼ) − (a₀ + … + aᵢ₋₁) = aᵢ + … + aⱼ. Every term from a₀ to aᵢ₋₁ appears once with a plus and once with a minus, so they cancel in pairs. When i = 0 the second bracket is empty and equals prefix[0] = 0.

Quick check 1 (predict)

NumPy’s np.cumsum on the first figure’s array [5, 2, 8, 1, 6] returns c = [5, 7, 15, 16, 22], same length, no leading 0. A colleague computes sum(1..3) as c[3] − c[1]. What do they get?

  • A. 11, the right answer
  • B. 9
  • C. 16
  • D. It raises an IndexError

Pick one before reading on.

Answer: B. c[3] − c[1] = 16 − 7 = 9, which is 8 + 1: it silently drops a[1], because c[1] already includes a[1]. That is the trap in treating cumsum’s output as the prefix array. With cumsum you would need c[3] − c[0], and a range starting at index 0 would need a special case, since c[−1] does not mean “nothing”. Prepending a 0 (prefix = [0, *cumsum]) gives n + 1 entries where prefix[k] means “everything before k”, and the one formula prefix[j+1] − prefix[i] covers every range, including i = 0.

Here is the trade. You pay O(n) time and O(n) extra memory once, to build the array. After that, every range sum costs O(1), so Q queries cost O(n + Q) instead of O(n·Q). The catch: the array has to stay put. Change one value and every prefix after it is stale, so you rebuild in O(n).

Quick check 2 (apply)

Running max works as a running total too: for a = [5, 1, 2] the prefix-max is [−∞, 5, 5, 5]. Can you get the max of a[1..2] from two prefix-max entries the way subtraction does for sums?

  • A. Yes: combine pmax[3] and pmax[1]
  • B. No: there’s no way to “un-max”
  • C. Only if the array is sorted

Pick one before reading on.

Answer: B. The max of a[1..2] is 2, but the entries you would use are both 5, and nothing you do to 5 and 5 can produce 2. It is tempting to think the trick carries over to any operation you can run as a running total, but subtraction works only because it undoes addition, and max has no undo. Xor does have one (x xor x = 0), so prefix-xor ranges work: for [5, 3, 6] the prefix-xor is [0, 5, 6, 0], and 3 xor 6 = 5 = p[3] xor p[1]. So a scan needs only associativity (to be parallelized); the range-query trick also needs an inverse.

The loop that won’t vectorize

Building the prefix array is a loop of n additions, and loops of additions are usually the easiest thing in the world to speed up, thanks to SIMD: single instruction, multiple data. One instruction operates on several values at once. An AVX register is 256 bits wide and holds eight 32-bit floats, so one vector add performs eight additions (AVX2 does the same for eight 32-bit integers). Each slot in the register is a lane. GPUs push the idea further: NVIDIA GPUs run threads in groups of 32, called warps, that execute the same instruction together, a scheme NVIDIA calls SIMT (single instruction, multiple threads).

Here are two loops that look almost the same:

c[k] = a[k] + b[k]        # independent adds
s[k] = s[k−1] + a[k]      # each add waits on the last

The first loop is a perfect fit for eight lanes, because its additions don’t depend on each other. The second isn’t: s[k] needs s[k−1], which needs s[k−2], all the way back to the start. One lane works while the other seven sit idle.

Quick check 3 (think, then read on)

The loop s[k] = s[k−1] + a[k] makes every add wait for the previous one, so 8 lanes sit idle. Think of a way to use 8 lanes to get just the total of [3, 1, 7, 0, 4, 1, 6, 3] in fewer than 7 rounds.

Think about it before reading on.

Answer. Add neighbours in pairs, all at once: (3+1), (7+0), (4+1), (6+3) gives 4, 7, 5, 9. Then pairs of those: 11, 14. Then 25. Three rounds instead of seven. This works only because addition is associative: the grouping can change without changing the result. The pairwise tree is exactly the first half of Blelloch’s algorithm, coming up shortly. The obvious loop’s dependency is real, but it belongs to that loop, not to the problem, so “a running sum is inherently sequential” turns out to be false.

Associativity means (3 + 1) + (7 + 0) equals ((3 + 1) + 7) + 0, so we are free to regroup the additions into independent pairs. That freedom is all the parallel algorithms below rely on. An operation that produces every running combination of an array like this is called a scan, and it works with any associative operator: +, max, xor and others. In an inclusive scan, output j includes a[j]; in an exclusive scan, output j combines only the elements before j. In those terms, the prefix array from the previous section is the exclusive scan with the grand total added at the end.

Hillis-Steele: everyone adds at once

The first parallel scan here is the one Hillis and Steele published in 1986, as described in GPU Gems 3, chapter 39. It assumes one lane per element, and every lane follows the same rule at the same time:

Each cell adds the value offset places to its left. The offset starts at 1 and doubles every step: 1, 2, 4. A cell with nothing that far to its left keeps its value.

After each step, every cell’s sum reaches twice as far back as before, so three steps cover all eight elements. Each step reads from one row and writes into a fresh one, which is why the figure stacks rows: the algorithm keeps two buffers. Updating in place would let a cell read a neighbour that had already been overwritten in the same step, and it would get the wrong sum.

Quick check 4 (predict)

Hillis-Steele took 3 steps for 8 elements (offsets 1, 2, 4). How many steps for 1,024 elements, assuming one lane per element?

  • A. 10
  • B. 32
  • C. 512
  • D. 1,023

Pick one before reading on.

Answer: A. Each step doubles the offset, and the scan is done once the offset has covered the whole array: 1, 2, 4, …, 512 is 10 offsets, so log2(1,024) = 10 steps. The catch is in the other number: each step does almost n adds, so 10 steps cost 9,217 adds, against 1,023 for the plain loop. That is O(n log n) additions in total. (32 would be right if each step squared the reach instead of doubling it; 1,023 is the plain loop’s count, where each add waits on the last.)

Blelloch: sum up a tree, then hand the sums back down

Blelloch’s scan, from 1990 and again as described in GPU Gems 3, chapter 39, avoids those extra additions. It works on a single array in two phases, with a small reset in between.

Up-sweep. This is the pairwise trick from check 3, done in place: in each pair, the right element becomes L + R. The pairs are 1 apart, then 2, then 4. After three levels the last position holds the total of the whole array, and the other right-hand slots hold the totals of smaller groups along the way.

Clear. Save the total, because you will want it, then put 0 in the last position. Nothing comes before the whole array, so 0 is the right value to start handing down.

Down-sweep. The value arriving at a pair from above, its parent, is the sum of everything to the left of that pair’s group; in the in-place array, the parent’s value sits in the right slot of the pair. The left element takes the parent’s value. The right element takes the parent plus the left element’s old value, because the left half of the group sits between it and everything before. The pairs are 4 apart, then 2, then 1.

Quick check 5 (predict)

Partway through the down-sweep the row is [3, 0, 7, 4, 4, 11, 6, 16]. After the last step (stride 1), what will the array be?

  • A. [3, 4, 11, 11, 15, 16, 22, 25]
  • B. [0, 3, 4, 11, 11, 15, 16, 22]
  • C. [0, 0, 3, 4, 11, 11, 15, 16]

Pick one, then check it against the full trace below.

Answer: B. Each pair (L, R) applies “L ← parent; R ← parent + old L”. For pair (4, 5), L gets 11 and R gets 11 + 4 = 15. Every position ends up holding the sum of everything before it: an exclusive scan. A is the tempting one, but it is Hillis-Steele’s inclusive answer, where each position includes itself, which is B shifted one place. C shifts twice.

The cost: 14 additions in 6 levels, against Hillis-Steele’s 17 additions in 3 steps. In general Blelloch does 2·(n − 1) additions (plus n − 1 swaps), which is O(n), the same order as the plain loop. That is why it is called work-efficient: its total additions, its work, grow like the plain loop’s. The price is about 2·log2(n) levels instead of log2(n).

Why does the down-sweep work? Follow position 5 through the last step. It is the R of pair (4, 5). The 11 sitting there came down from its parent, and it is the sum of everything to the left of this pair: 3 + 1 + 7 + 0. Position 4 (L) simply takes that 11, which is everything before position 4. Position 5 adds the old L value, 4, to get 15 = 3 + 1 + 7 + 0 + 4, which is everything before position 5. The same holds at every level: a parent’s value is “everything left of my group”, and each child gets “everything left of me”.

Fewer steps isn’t faster: work vs. span

You have now counted two different things for each algorithm, and they deserve names. Span is the number of steps if lanes were unlimited: the loop’s 7, Hillis-Steele’s 3, Blelloch’s 6. Work is the total number of additions: 7, 17 and 14. At n = 8 the difference in work looks small. Here is how it grows.

Hillis-Steele has the smallest span, log2(n), and the largest work, a factor of about log2(n) more than the loop. Which of the two numbers decides the running time depends on how many lanes you actually have.

Quick check 6 (predict)

You scan a million floats on a CPU with 8 AVX lanes. Rank the plain loop, Hillis-Steele, and Blelloch from fastest to slowest (by rounds of adds, ignoring memory).

  • A. Hillis-Steele, Blelloch, loop: fewest steps wins
  • B. Blelloch, Hillis-Steele, loop
  • C. Blelloch, loop, Hillis-Steele
  • D. All about the same

Pick one before reading on.

Answer: C. With 8 lanes, each round does at most 8 adds, so time is roughly work ÷ 8. Hillis-Steele does ~19.9M adds, so ~2.5M rounds: worse than the loop’s ~1.05M. Blelloch does ~2.1M adds, so ~262k rounds, about 4× fewer rounds than the loop. A is the tempting answer, because step count is the number everyone quotes, but Hillis-Steele’s “only 20 steps” assumes a million lanes. Fewer steps wins only when lanes ≥ elements.

Rule of thumb, in this adds-per-round model. When you have at least as many lanes as elements, as when one 32-thread warp scans 32 values, Hillis-Steele’s fewer steps win and its extra adds ride on lanes that would otherwise sit idle. When elements vastly outnumber lanes, as with a million floats on 8 AVX lanes, every add costs a lane-slot, and Blelloch’s smaller work wins.

Back to O(1)

Time to put the two halves together. A GPU running Blelloch’s scan hands you back an array and one saved number. Here is what they are good for.

Quick check 7 (apply)

A GPU just ran Blelloch on [3, 1, 7, 0, 4, 1, 6, 3] and returned [0, 3, 4, 11, 11, 15, 16, 22], plus the saved total 25. What is sum(2..5), and which two entries give it?

  • A. 12 = 16 − 4
  • B. 11 = 15 − 4
  • C. 13 = 16 − 3
  • D. 8 = 11 − 3

Pick one before reading on.

Answer: A. Blelloch’s output is prefix[0..7] and 25 is prefix[8], so sum(2..5) = prefix[6] − prefix[2] = 16 − 4 = 12 (= 7 + 0 + 4 + 1). B uses prefix[5], which is “everything before 5” and so drops a[5]: that’s the j versus j + 1 slip. C starts one too early: 16 − 3 = prefix[6] − prefix[1] = sum(1..5), which includes a[1]. D uses the wrong entries at both ends.

Recap

  • Build the prefix array once, with a plain O(n) loop or a parallel scan, and any range sum is prefix[j+1] − prefix[i] in O(1), with no special case at i = 0.
  • The subtraction trick needs an operation you can undo: + and xor, not max.
  • Hillis-Steele takes the fewest steps, log2(n), but does O(n log n) work: best when lanes ≥ elements.
  • Blelloch does O(n) work in about 2·log2(n) levels: best, counting adds per round, when elements far outnumber lanes.

Where next. If values change after the build, look at Fenwick trees, which avoid the full rebuild; and arrays too large for one pass are scanned in blocks. Real CPU code combines Hillis-Steele with the plain loop: it scans each 8-lane register with Hillis-Steele (there, lanes = elements) and carries the running total from block to block, one block after another. Once the array outgrows the cache, memory bandwidth, not additions, sets the speed.
